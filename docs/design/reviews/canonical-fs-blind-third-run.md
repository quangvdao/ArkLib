`KnowledgeGames` imports the state-restoration game and query-log modules. `SingleSalt` imports `KnowledgeGames`, `Lifting`, `DeriveTranscript`, and a query-bound module. The protocol is a `ProtocolSpec n`; its `Messages` contains one prover message at every prover-message index, while a full transcript includes prover messages and verifier challenges. At each challenge index, `srChallengeOracle` takes the statement and the preceding prover-message prefix as its query input. `fsChallengeOracle` is an alias of that oracle specification. The single salt is incorporated by using the pair `(x,salt)` as the challenge-oracle statement.

## The adaptive NARG game

The proof type is `FSSaltedProof pSpec Salt = Salt × pSpec.Messages`. `singleSaltFiatShamir V` takes an unsalted input `x`, reads the prover-chosen salt and messages from the proof, derives the full transcript by querying `fsChallengeOracle (StmtIn × Salt)` at `(x,salt)` and the appropriate message prefixes, then runs `V.verify x transcript`. The salt is not sampled by this verifier. `saltedIPVerifier V`, used on the state-restoration side, receives `(x,salt)` but runs `V.verify x transcript`, ignoring the salt in `V` itself.

In `adaptiveNARGKnowledgeSoundnessExpWithCoins`, the common source-oracle state is sampled once from `init : ProbComp σ`. The prover `P` runs first on `oSpec + auxSpec` and returns `(x,π)`. Its queries are logged; only the `oSpec` projection of that prover log is handed to the extractor. Next the noninteractive verifier runs on the **same evolving source-oracle state** and its `oSpec` queries are logged. Then the extractor runs, again continuing from that state, and may query `oSpec + auxSpecE`. The two auxiliary implementations have types `QueryImpl auxSpec ProbComp` and `QueryImpl auxSpecE ProbComp`; the theorem supplies them separately. The extractor receives `x`, the whole proof `π`, the prover's `oSpec` query log, and the verifier's `oSpec` query log. Its input type provides neither the prover's private random tape, its auxiliary query log, the verifier's output, nor direct access to the source state as an argument. Its oracle calls may nevertheless observe the state through the supplied implementation. The extractor runs even when the verifier returns `none`.

The result is `(x, Option WitIn, Option StmtOut)`. The NARG failure event is false on verifier rejection (`stmtOut? = none`). For `some stmtOut`, it is `stmtOut ∈ langOut` and either the extractor returned `none`, or it returned `some witIn` with `(x,witIn) ∉ relIn`. In particular, an accepted output paired with no witness counts as failure. The probability is **unconditional** over the experiment's randomness: `langOut` is tested inside the event, rather than conditioning or renormalizing on acceptance. The predicate `bound P` restricts which prover programs the quantified theorem considers; it is not an event conditioned on a run.

`Verifier.adaptiveNARGKnowledgeSoundnessWithCoinsWithExtractor` means `∀ P, bound P → Pr[failure for that fixed extractor and P] ≤ error`. The version without `WithExtractor` means `∃ extractor, ∀ b,` that fixed-extractor statement holds for `bound b` and `error b`. Thus one extractor is selected **before** every budget parameter and every bounded prover; it is not chosen after seeing a particular `P` or its coins. The extractor program can use its allowed oracle interface, but no explicit running-time or extractor-query bound appears in this proposition.

## The state-restoration coin game and delegation

`Prover.StateRestoration.KnowledgeSoundnessWithCoins` is a program on `(oSpec + srChallengeOracle StmtIn pSpec) + auxSpec` returning `(statement,messages,outputWitness)`. The coin experiment samples `init : ProbComp (QueryImpl (srChallengeOracle StmtIn pSpec) Id)` once. An `oSpec` implementation acts in `StateT` over that sampled query implementation, and `srChallengeQueryImpl'` answers a challenge query by applying the *current* state function and leaving it unchanged. The prover runs, yielding a logged triple; the game derives the transcript, runs and logs the interactive verifier, then runs the state-restoration extractor. These phases continue the same state, so changes made by the `oSpec` implementation can be visible to later phases; the source does not resample the state between them. The challenge query implementation itself is a read of the current function. There is no requirement in these game types that `init` be a uniformly sampled or independently keyed random function, nor that `oSpec` preserve that function.

The state-restoration extractor type takes the statement, output witness, full transcript, prover query log for `oSpec + srChallengeOracle`, and verifier query log for `oSpec`, then runs an optional `oSpec` oracle computation yielding `WitIn`. Its coin-game failure event is false when the verifier returns `none`. If the verifier returns `some stmtOut`, failure means `(stmtOut,witOut) ∈ relOut` and the extractor returns `none` or an input witness outside `relIn`. `knowledgeSoundnessWithCoinsWithExtractor` universally quantifies the state-restoration prover under its `bound`; `knowledgeSoundnessWithCoins` existentially chooses one extractor before quantifying all budget parameters and bounded provers.

For a Fiat–Shamir prover `P` returning `(x,(salt,messages))`, `srInducedProverKS P` only rearranges the output to `((x,salt),messages,())`; it does not add oracle queries or select a new salt. The transferred input relation `relInSalted relIn` checks `(x,witIn) ∈ relIn` and ignores the salt. The transferred output relation `unitOutputRelation langOut` checks `stmtOut ∈ langOut` and ignores its unit witness. This makes the two failure events correspond after the rearrangement.

Given a state-restoration extractor `E`, `fsSRDelegatingExtractor E` passes it `(x,salt)` and unit output witness. It constructs a full transcript from the proof's messages and challenges recovered from the verifier's Fiat–Shamir challenge-query log, passes the entire projected prover `oSpec + fsChallengeOracle` log, and passes only the verifier's `oSpec` log. `Messages.challengesOfLog` looks up the **first** matching challenge-query entry for each canonical `(x,salt,message prefix)` key; if the key is absent it supplies the type's default challenge. The logged actual verifier execution is linked in the code to a canonical challenge log, but the extractor definition itself has this default behavior on arbitrary logs. `fsSRDelegatingNargExtractor` merely lifts the `oSpec`-only delegating extractor into the larger NARG extractor oracle interface. It does not issue `fsChallengeOracle` or `auxSpecE` queries itself.

## The SR-to-FS theorems

`single_salt_fiat_shamir_knowledge_soundness_of_fixedExtractor` takes a particular `E`, a state-restoration prover predicate `srBound`, a Fiat–Shamir prover predicate `bound`, a common error `ε : ENNReal`, and the transfer hypothesis `∀ P, bound P → srBound (srInducedProverKS P)`. It also assumes the state-restoration coin-game bound for this **same** `E`, using the same `fsInit`, `fsImpl`, `auxImpl`, salted input relation, unit output relation, and `saltedIPVerifier V`. It concludes the adaptive NARG coin-game bound for `singleSaltFiatShamir V` and `fsSRDelegatingNargExtractor E`, with prover-side source implementation `fsImpl.addLift srChallengeQueryImpl'`, the given `auxImpl`, and arbitrary extractor-side `auxImplE`, at exactly error `ε`. There is no extra error term or explicit numerical query loss in this theorem; any restriction on prover query behavior must come from the supplied `bound` and `srBound` predicates and their implication.

`single_salt_fiat_shamir_knowledge_soundness` quantifies a budget type `B`, predicates `srBound b` and `bound b`, and an error function `ε b`. Its transfer hypothesis is `∀ b P, bound b P → srBound b (srInducedProverKS P)`. It assumes `Verifier.StateRestoration.knowledgeSoundnessWithCoins`, which is `∃ E, ∀ b, ∀ srProver, srBound b srProver → Pr[SR failure] ≤ ε b`. It concludes `Verifier.adaptiveNARGKnowledgeSoundnessWithCoins`, meaning `∃ FS extractor, ∀ b, ∀ P, bound b P → Pr[NARG failure] ≤ ε b`; the proof chooses the delegated extractor from that one SR extractor. The stated reduction does not prove the SR assumption or the bound-transfer implication; both are premises. The auxiliary extractor oracle implementation is a parameter of the conclusion but the delegated extractor does not use it.
