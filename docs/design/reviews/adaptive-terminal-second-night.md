## Literal mathematical readback

`QueryProgram config rounds Y depth` is an inductive, finite-depth deterministic decision tree (lines 32–37). At any indexed depth it may terminate with a Boolean. A request at index `depth+1` carries a `QuerySite` and a continuation `List Y → QueryProgram ... depth`; hence `depth` bounds the number of requests along every path, rather than requiring exactly that many. `QuerySite` carries a `Fin rounds` slot, tag, and selector for that tag's skeleton (imported `MerkleTerminalBatch.lean:33–36`). The next site can depend on the list of selected values returned at the previous request; it has no explicit input of roots, proof paths, oracle/cache state, or the full opening, although a separately constructed program can close over external values. `ofSites` embeds a fixed sequence and a decision on the ordered lists of selected answers (lines 41–50).

The terminal protocol remains the imported one: the prover sends `rounds` pairs `(tag, root)` in order, then sends one complete list of `PublicOpening`s at the terminal node (`MerkleTerminalBatch.lean:71–80`). Each opening carries a claimed site and a typed batch opening. The verifier obtains this whole list before executing `verifyBatch` (new lines 126–153); this code does not implement an interactive sequence in which the verifier sends the chosen next site to the prover. It verifies *every submitted opening* against the root at its public slot using `verifyOpeningClaims`, then checks the path selected by the program. The check accepts iff the root list has length `rounds`, every program request consumes exactly one submitted opening with matching tag, slot and selector, that site's slot has the expected tag in the roots, its selector has a selected leaf, all verification attempts accept, the program terminates with `true`, and no submitted openings remain (new lines 69–95, 126–135; imported `siteMatches` at 145–152). The selected leaf values are flattened left-to-right. The explicit selected-value length equality in `requestValid` follows from the dependent `SelectedValues` type and `selectedValuesList_length` (new lines 53–64, 75–76); the nonempty-selector check is already entailed by the existence of a `BatchOpening` once selectors match (`Opening.lean:29–40`). These checks do not independently add security.

`idealDecision` (new lines 99–122) runs the same finite decision tree using selected leaves of `extractA` from the stored checkpoint at each chosen slot, replacing absent extracted leaves by the supplied `fallback`. It checks root-list length, expected tag at each slot, and nonempty selector, but it does not inspect submitted openings. A checkpoint is a root and cumulative query log at the end of the corresponding commit phase (`Stateful.lean:72–86, 109–129`); `extractA` derives a partial tree from that log and root, then fills `none` leaves with `fallback` (`MerkleTerminalBatch.lean:203–209`). The ideal decision therefore depends on the deterministic program, model view, recorded commit prefixes, fallback, and roots, not on a fully materialized committed tree or an independent codeword predicate.

The new native game runs the imported prover strategy and a verifier strategy whose terminal action is `verifyBatch`; it starts a random-oracle cache overlay at empty (`new:139–175`). `nativeSuffix_eq_source`, `nativeGame_eq_source`, and `coupledExperiment_native_eq` establish equality of these OracleComp computations after the specified projections, by comparing the strategy runner with sequential commitment execution, terminal opening, and verification (`new:213–394`). The coupled experiment comes from the imported batch module: it runs the same committer and opening, then verifies claims equipped with the recorded checkpoint and retains attempts, logs, roots and openings (`MerkleTerminalBatch.lean:575–590`). The public-root verification and checkpoint-root verification have matching acceptance bits under the imported bridge (`new:347–381`). These are game equalities, not probabilistic security statements.

For a coupled transcript in support, its roots equal those of its extractor state and its attempts align with submitted openings by construction (imported `MerkleTerminalBatch.lean:750–754, 818–849`). If the real coupled acceptance bit is true and the upstream checkpoint disagreement event is false, every selected submitted answer equals the selected extracted answer at the matching checkpoint. Induction over the program's depth then yields `idealDecision = true` (`new:434–593`). The upstream disagreement event is a disjunction: an accepted opening differs from the checkpoint-extracted opening, two equal-root checkpoints extract differently, or terminal suffix queries change a checkpoint extraction (`Stateful.lean:320–328, 334–366`; `Game.lean:188–193`). Only the accepted-opening component is used in the local implication, while the larger event is what the imported ROM theorem bounds.

For any such program and adversary, under `EvalDistSemantics` and `LawfulEvalDistSemantics`, the real acceptance probability is at most the ideal acceptance probability plus the probability of that upstream disagreement event in `extractabilityExperiment` of the converted owner adversary (`new:595–664`). The converted adversary shares the committer and maps each terminal public opening to a claim at its recorded checkpoint (`MerkleTerminalBatch.lean:266–271`), and the imported game equality couples its distribution to the new one. No independent bound on ideal acceptance is proved here.

Under finite inhabited output `Y`, discrete measurable output, a uniform random-oracle measure, decidable equalities, and five natural-number budgets, the probability of real acceptance is at most ideal-core acceptance plus
`multiCheckpointROMErrorNumerator nodeBudget checkpointCount verifierOverhead queryBound / Nat.card Y` as an `ENNReal` expression (`new:721–756`). The assumptions are: the converted adversary's full commitment-plus-opening prefix is totally query bounded by `queryBound`; every possible converted opening emits claims whose total verifier query count is at most `verifierOverhead`; all configuration node budgets are at most `perCheckpoint`; `rounds * perCheckpoint ≤ nodeBudget`; and `rounds ≤ checkpointCount` (`ResourceBounds.lean:186–213`). The numerator is the supremum over `prefixMisses = 0,...,queryBound` of `prefixMisses.choose 2 + min nodeBudget (2*prefixMisses + checkpointCount) * (queryBound + verifierOverhead)` (`Potential.lean:62–79`). The imported ROM theorem bounds the disagreement event with precisely these assumptions (`StrongBound.lean:518–535`). The ideal-core experiment runs only the commitment prefix inside an empty cache overlay and applies `idealDecision` to its extractor state and roots; it omits terminal opening and verification (`new:421–430`). A reused imported suffix-skipping probability theorem shows the ideal acceptance event has the same probability as this core event under the uniform measure (`new:668–716`; imported `MerkleTerminalBatch.lean:1172–1206`).

The final theorem adds an explicit hypothesis that the ideal-core acceptance probability is at most an arbitrary `η : ENNReal`, and concludes real acceptance is at most `η` plus the same ROM error (`new:760–787`). It supplies no theorem establishing that hypothesis, no restriction that `η < 1`, and no resource bound on the decision-tree computation itself. The quotient can be at least one, making the numerical inequality uninformative for some parameter choices; that is a parameter-regime limitation, not a logical inconsistency. A caller may also choose an always-accepting `.done true` program and `η = 1`; the theorem is then formally true but gives no cryptographic soundness. The source asserts a conditional reduction from real acceptance to ideal-core acceptance, not soundness of any particular ideal predicate or proof system.
