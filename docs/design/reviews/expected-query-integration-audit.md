## What the main theorem actually says

`OracleComp.prEvent_randomOracle_le_expectedFreshQueryCharge` (`ExpectedFreshQueryInfinite.lean:80-88`) accepts any `oa : OracleComp (unifSpec + ofFn R) α` with `DecidableEq D` and finite, sampleable reply types (`SampleableType (R d)`). `D` itself need not be finite. `event : α → Prop` must, **for every complete answer assignment `g` and every supported fixed-table logged run `z` from empty cache**, imply a witness `t` among the distinct keys in *that run's* ordered log with `bad t g`. For every `t,g`, independently resampling only cell `t` must make `bad t` occur with probability at most `error t`. Then the event probability in the actual lazy cached run is at most `expectedFreshQueryCharge oa error`: the Lebesgue expectation of the sum of `error` over the distinct keys in its actual log (`LoggedRun.lean:205-214`). This charges failure values if `α` contains them, because they remain returned values in the logged run. It does **not** bound runtime, make a reduction to an adversary, or turn a per-key error assumption into one by itself. The cache is empty in this public theorem; #826 extends to a fixed initial cache.

## Why the PR is long

GitHub reports 1,330 added / 25 deleted lines across six files. Gross additions by layer: `LoggedRun.lean` 285 (joint interpreter and charge), `ExpectedFreshQuery.lean` 545 (finite-table law, own-cell invariance, probability/union argument), `FiniteSupport.lean` 340 (retype a finite program to its reachable hash keys, preserve run/log/cache/charge), `ExpectedFreshQueryInfinite.lean` 121 (support witness and final transfer), `FreshQuery.lean` 35 added / 25 deleted (mostly exposing previously private restriction helpers), umbrella 4. The central mathematical route is roughly: lazy/eager equality `ExpectedFreshQuery.lean:28-147`; own-cell query-occurrence invariance `:161-237`; per-cell event factor and integral `:251-362`; finite union-to-expected-charge `:433-459`; finite interleaved theorem `:485-543`; finite restriction and reembedding `FiniteSupport.lean:35-338`; arbitrary-domain transfer `ExpectedFreshQueryInfinite.lean:80-119`. This is a joint law, not merely an output probability: interleaved private randomness, cache hits, ordered log, final cache, adaptive next queries, and failure-returning branches must all agree. The restriction work is needed because a global uniform table over an infinite input type is unavailable, while finite OracleComp syntax with finite response branching yields finite possible hash keys.

## Owner APIs and integration

The new interpreter composes existing components, rather than implementing a second cache: `randomOracleLoggedRun` uses `(ofFn R).randomOracle.withLogging` and `unifSpec.passthrough` (`LoggedRun.lean:86-101`); `fixedTableLoggedRun` uses `QueryImpl.ofFn`, `liftTarget`, `withCaching`, `withLogging` at the same lines. The project already has `QueryImpl.withCachingLogging` in `CachingLoggingOracle.lean:49-78`, but that returns `StateT (cache × log)` whereas #824's `WriterT log (StateT cache ...)` preserves an ordered log with natural bind concatenation. Switching encodings would require a proven state/writer isomorphism, not a simple alias. `randomOracleLoggedRun_project` (`LoggedRun.lean:218-283`) links back to the existing `romImpl`; this bridge is appropriate. The 65-line induction may be reducible using generic projection laws in `LoggingOracle/Core.lean:94,196` or state-projection infrastructure, but no immediate drop-in law was established.

The distinct-key charge is a **postprocessing of the completed log** (`freshKeysOfLog` uses `List.toFinset` at `LoggedRun.lean:31-46`). Existing `CostModel.queryCost` (`CostModel.lean:63-87`), `withAddCost` (`WriterCost.lean:41-78`), and current-main `expectedSimulatedQueryCount` (`ExpectedQueryCount.lean:64-74`, read via GitHub at `9146f78`) charge each query occurrence using an index-only predicate/cost. They do not charge a repeated key only once. `AddWriterT.expectedCost` (`WriterCost.lean:217-253`) can express the final integral after a bridge from the log, but cannot eliminate the cache/log semantics or the own-cell resampling proof. `expectedSimulatedQueryCount` is new on current main, not in #824's base, and also has different semantics; avoid claiming #824 overlooked a pre-existing equivalent.

The arbitrary-domain restriction reuses `possibleQueryKeys`, `allQueriesSatisfy_possibleQueryKeys`, `restrictCache`, and `extendTable` from `FreshQuery.lean:332-520`, exposed by this PR from private declarations. It does not simply reuse `restrictQueries` (`FreshQuery.lean:376-394`) because that targets `ofFn R` only; the new program has a `unifSpec + ofFn R` query sum and must leave private draws alone. It does duplicate the proof pattern. Generic `AllQueriesSatisfy` and `SubSpec` APIs exist, but `SubSpec` lifts a *small* spec into a larger one; restriction requires retyping reachable queries in the reverse direction, so `SubSpec` alone does not replace this construction. Current main's `AllQueriesSatisfy.simulateQ_run_eq_map_run'` (`QueryBound/Simulation.lean:789-805`) assumes the handler leaves state unchanged, so it cannot prove this cache/log preservation.

## Refactor candidates, ranked

1. **Remove or split the unused pure-table side route (~95-110 lines, low/moderate effort).** `LoggedRun.lean:48-81` defines `tableFreshKeys` and proves update invariance; `ExpectedFreshQuery.lean:374-428` proves `prEvent_tableFreshKey_bad_le`, and `:462-475` proves `prEvent_tableFresh_bad_le_expectedCharge`. Repository-wide search of VCVio/Examples/LatticeCrypto/HashSig at #824, plus the local #826 integration, found no consumer of the final pure-table theorem or the `tableFreshKeys` API outside this side route. The actual final theorem uses `prEvent_interleavedFreshKey_bad_le` (`:277`) and the generic finite-union lemma (`:433`). Unless a named downstream consumer needs the pure theorem, delete the side route or isolate it in an optional module; this is the clearest direct reduction in PR size without weakening #824's advertised theorem. Verify import users before deleting public declarations.

2. **Move the general probability lemmas to their owner layer (~50 lines relocated, moderate effort).** `prEvent_bind_and_factor` (`ExpectedFreshQuery.lean:251-273`) is generic over two `ProbComp`s and contains no random-oracle concept. `prEvent_bad_in_freshKeys_le_expectedCharge` (`:433-459`) is generic over any finite key type, observed key set, and `ProbComp β`; #826 reuses it in `InitialCacheExpectedQuery.lean:188`. Put the first in EvalDist probability/event helpers and the second near expectation/observed-cost machinery, with narrow imports. This improves reuse and module ownership but mostly moves lines; it does not eliminate the core proof.

3. **Generalize finite query-support/retyping once (~medium-to-large refactor, uncertain net savings).** `FreshQuery.lean:332-394` and `FiniteSupport.lean:35-108` each compute finite support and recursively retype queries; the latter filters the `Sum.inr` keys and retains `Sum.inl` private draws. A generic predicate-indexed finite support/retyping combinator at the `OracleComp`/QueryBound layer, with a law for stateful handler transport, could share these and future constructions. `FiniteSupport.lean:157-271` currently proves lazy/fixed transport separately but with nearly identical pure, private draw, cache-hit and cache-miss skeletons. A handler-parametric transport theorem may unify them, provided cache/log state mapping and sampleable replies are stated cleanly. This is a separate API project and may increase abstraction overhead; don't require it solely to merge #824.

4. **Hoist `AllQueriesSatisfy` monotonicity and trim a support corollary (small).** `FiniteSupport.lean:56-64` proves private `allQueriesSatisfy_mono'`; `FreshQuery.lean:360-368` contains the same induction locally inside `allQueriesSatisfy_possibleQueryKeys`. A public `AllQueriesSatisfy.mono` beside `QueryBound/Basic.lean:455-501` would remove two local proofs and simplify future restriction code. `ExpectedFreshQueryInfinite.lean:28-73` proves a strong fixed-table support witness, yet it is not used in `:80-119`; retain it if a named Merkle or other consumer needs that joint trace witness, otherwise separate it from the minimal expected-bound module (~46 lines). This is a discoverability/size choice, not a correctness defect.

No demonstrated mathematical bug or direct owner-API equivalent emerged from this audit. The strongest immediate simplification is deleting/separating the unused pure-table branch. The stateful joint law and finite-support transport are substantive obligations; replacing the theorem by existing per-query cost counting would change its distinct-key expected-charge guarantee.
